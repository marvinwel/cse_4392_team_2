ADDITIONAL CLASSIFICATION CHECKS

1. Resolve synonyms, naming phrases, and short/full forms before classifying. A statement that one concept is "known as" another name does not establish a subclass. Keep one canonical class unless the description establishes distinct objects. Prefer the noun used as the subject of domain facts over a term introduced only as another name. If both a modified noun and its shorter head noun refer unambiguously to the same object, use the shorter source form consistently.
2. Model the core domain. Input hardware, entry methods, and generic processing words do not require classes merely because they are nouns. Include them only when the description requires their independent domain identity or stored information.
3. Assign each descriptive attribute to the concept actually described by its sentence, after resolving aliases. Do not move attributes to a duplicate role class. If a verb's object is a scalar attribute, do not create an association to the attribute owner's class as a substitute.
4. For active and passive clauses, resolve the actor, recipient, and thing acted upon separately. Distinguish the actor's action from a persistent possession relationship created for the recipient. Include only relationships between supported classes; procedural scanning, entry, and update steps do not automatically imply persistent domain relationships.
5. Audit all state and quantity phrases as well as nouns. A verb can describe a stored state or relationship-specific fact rather than another association. Give such a fact to the object or association whose state it describes, when the source requires that information. Values and multiplicity limits are not separate classes.
6. Review every association for the two association-class conditions: many-to-many participation and information about the relationship that must be retained. Use only source-supported state or data. Do not invent conventional fields to justify an association class.
7. Audit coverage of the fixed inventory, including omissions, but output only the final classification in the required format. Do not force every phrase into an element or rely on outside domain conventions.

<domain_description source="library-1.docx">
A library issues loan items to customers. Each customer is known as a member and is issued a membership card that shows a unique member number. Along with the membership number other details on a customer must be kept such as a name, address, and date of birth. The library is made up of a number of subject sections. Each section is denoted by a classification mark. A loan item is uniquely identified by a bar code. There are two types of loan items, language tapes, and books. A language tape has a title language (e.g. French), and level (e.g. beginner). A book has a title, and author(s). A customer may borrow up to   a maximum of 8 items. An item can be borrowed, reserved or renewed to extend a current loan. When an item is issued the customer's membership number is scanned via a bar code reader or entered manually. If the membership is still valid and the number of items on loan less than 8, the book bar code is read, either via the bar code reader or entered manually. If the item can be issued (e.g. not reserved) the item is stamped and then issued. The library must support the facility for an item to be searched and for a daily update of records.
</domain_description>

Class or Attribute? More Rules to Apply
Rules to apply:
Attributes describe objects or store state information of objects.
Attributes are of scalar types such as int, double, string, char and boolean; classes are not.
You can enter attribute values from the keyboard, but you cannot do so for objects.
Objects must are created by invoking a constructor.
